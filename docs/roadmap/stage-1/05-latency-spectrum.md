# 05 · 业务形态与时延谱系

> 📍 阶段一 · 知识整理 05 ｜ 核心模型：时延谱系——后续每学一个协议都往这张表里放

## 三种业务形态

| 形态 | 内容状态 | 交互性 | 追求 |
| --- | --- | --- | --- |
| **点播（VOD）** | 已存在 | 仅 seek / 倍速 | 起播快、不卡顿、seek 流畅 |
| **直播（Live）** | 正在产生，单向 | 弹幕级 | 时延与流畅的平衡 + 分发成本可控 |
| **实时互动（RTC）** | 正在产生，双向 | 强（对话） | 端到端时延 < 400ms |

为什么 RTC 要求 < 400ms：人类对话中，端到端时延超过约 400ms 就会出现抢话、尴尬停顿，优秀产品会做到 200ms 量级。这是生理约束，不是工程约束。

## 时延谱系（必背）

| 方案 | 典型端到端时延 | 传输层 | 备注 |
| --- | --- | --- | --- |
| 文件下载 / 渐进式 | 分钟级 | HTTP | 点播特有 |
| 传统 HLS | 10~30s | HTTP (TCP) | 切片时长决定时延下限 |
| LL-HLS / LL-DASH | 2~5s | HTTP (TCP) | Part 分片 + 阻塞请求 |
| HTTP-FLV / RTMP 拉流 | 2~5s | TCP 长连接 | CDN 友好 |
| SRT | 1~3s | UDP | 应用层可靠重传 |
| WebRTC / RTC | 0.1~0.4s | UDP (RTP) | 互动级 |

两条规律：

1. **传输单元粒度**（文件 → 切片 → 帧）越细，时延越低；
2. **传输层**从 TCP 换到 UDP，才能突破 TCP 重传与队头阻塞的限制，进入亚秒级。

> 阶段二逐个学协议时，把每个协议按这两个维度归位；阶段四的 QUIC/MoQ 也是在这个坐标系里找位置。

## 为什么不能「又要 <1s 又要绝不卡」

- 网络带宽是波动的，播放端必须有**缓冲区**来吸收抖动（阶段三的 jitter buffer）。
- 缓冲越深 → 抗抖动越强、越不卡，但数据在缓冲区里排队 → 时延越大。
- 所以「时延-流畅」是一条权衡曲线，不同产品在曲线上选点：

```mermaid
flowchart LR
    A["文件下载 / 渐进式<br/>分钟级"] --> B["传统 HLS<br/>10~30s"] --> C["LL-HLS / HTTP-FLV<br/>2~5s"] --> D["SRT<br/>1~3s"] --> E["RTC<br/>0.1~0.4s"]
```

越往右，时延越低、流畅性越难保：每往右一步，都要求更深的工程投入（更细的传输单元、更激进的缓冲策略、更强的拥塞控制）。

- RTC 的先进之处：不是把缓冲清零，而是用**拥塞控制 + 快速重传 + 动态码率**把整条曲线左移。

## 音画同步：问题从哪来

时延谱系里越往左（越实时），音画同步越难。不同步的来源：

- 音视频**采集路径不同**：麦克风直采延迟低，摄像头有缓冲，两者时间戳不同源；
- **编码耗时不同**：B 帧让视频比音频晚；
- **网络分路抖动**：音视频分路传输、到达时间不一致；
- **解码与渲染耗时不同**。

解决思路（概念层，阶段三细化）：

- 全链路**统一时间基**：时间戳 + 对齐时钟（NTP / RTCP SR）；
- 播放端选一个**主时钟**（通常是音频），视频帧按时基对齐渲染；
- 必要时丢帧或重复帧追齐（RTC 播放端的常态操作）。

## 产品对照

- 点播：B 站 / YouTube 视频
- 直播：抖音 / 斗鱼直播（传统 HLS~FLV 系）；电商与拍卖用的超低延迟直播（3s 内）
- RTC：Zoom、腾讯会议、微信视频通话、直播连麦 PK

## 关键要点

- 时延谱系：HLS(10s+) → LL-HLS / FLV(2~5s) → SRT(1~3s) → RTC(<0.4s)。
- 时延由「传输粒度」与「传输层」共同决定；缓冲深度是时延与流畅的交换。
- 音画同步 = 统一时间基 + 主时钟调度；越实时越难。
