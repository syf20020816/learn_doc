# 04 · 封装与容器

> 📍 阶段一 · 知识整理 04 ｜ 重点：moov 位置与点播首开的关系——工程实践中的经典坑

## 为什么需要封装

编码器的输出是各自独立的裸流（H.264 视频流、AAC 音频流）。播放器拿到一堆裸流无法工作，它需要知道：

- 哪段数据是视频、哪段是音频、哪段是字幕（**多轨组织**）；
- 每个包应该在什么时刻播放（**时间戳 / 同步**）；
- 想跳到 10:00 该从文件的哪个字节开始读（**索引 / seek**）；
- 用什么解码器、分辨率多少、采样率多少（**元数据**）。

封装格式（container）就是回答这些问题的打包规范：**多轨 + 时间戳 + 索引 + 元数据**。

## MP4：点播之王

MP4 由一串 box 组成，最重要的是两个：

- `moov`：索引与元数据（怎么解、有多少轨、每轨数据在哪）；
- `mdat`：真正的媒体数据。

**moov 的位置决定播放体验**：

| moov 位置 | 后果 |
| --- | --- |
| 文件末尾（录制/转码的默认输出） | 必须拿到完整文件才能解析索引 → 无法边下边播，首开极慢 |
| 文件开头（**faststart**） | 下载文件头几 KB 就能起播 → 点播网站标配 |

**fMP4（fragmented MP4）**：把媒体切成一段段 fragment，每段自带 `moof` 小索引 → 支持边录边播、独立切片分发 → 正成为 HLS/DASH 切片与直播录制的新默认，逐步统一点播与直播格式。

## TS：直播与广电的经典

MPEG-TS 的设计目标是在不可靠信道（广播电视）上播放：

- 固定 **188 字节**小包，无全局索引；
- 可从任意位置开始解码（配合周期性插入的节目信息）→ **抗丢包、天然支持切片拼接**；
- 代价：包头开销约 5%~10%，不适合点播 seek；
- 所以 HLS 选它做 2~10 秒的直播切片（新趋势是 fMP4 切片替代）。

## FLV：RTMP 时代的轻量流

- 结构极简：一个 header 之后就是连续的 tag，流式友好；
- 与 RTMP 绑定使用了近二十年（HTTP-FLV 播放也靠它）；
- 正被 fMP4/TS 取代，但存量直播链路依然庞大（阶段二会反复遇到）。

## MKV / WebM：开源阵营

- **MKV**：全能容器，多音轨、多字幕能力最强，本地收藏与压制常用；浏览器不原生支持。
- **WebM**：Google 推出的 Web 容器（VP9/AV1 + Opus），本质是 MKV 的子集，配合开源编解码器使用。

## 容器对比表

| 容器 | 流式友好 | 索引/seek | 开销 | 典型场景 | 现状 |
| --- | --- | --- | --- | --- | --- |
| MP4（传统） | ❌ moov 后置时 | ✅ | 低 | 本地文件、下载 | 需 faststart 处理 |
| MP4（fMP4） | ✅ | ✅ | 低 | 点播、HLS/DASH 切片 | 主流方向 |
| TS | ✅ | 弱 | 高（~10%） | HLS 切片、广电 | 稳定存量 |
| FLV | ✅ | 弱 | 低 | RTMP / HTTP-FLV | 存量为主 |
| MKV | 一般 | ✅ | 低 | 本地播放、压制 | Web 之外 |

## moov 与点播首开（重点）

点播首开的完整过程：

```mermaid
flowchart LR
    A["点击播放"] --> B["请求元数据（moov）"] --> C["选清晰度"] --> D["拉取数据直到覆盖一个 I 帧"] --> E["解码"] --> F["首帧上屏"]
```

moov 后置时，播放器必须先发 Range 请求去文件尾部抓 moov——对象存储上多一次完整 RTT 往返，弱网或文件巨大时首开直接劣化。工程规矩：

> **所有上传/转码产物一律 faststart 化**（如 `ffmpeg -movflags +faststart`），并把「moov 是否前置」纳入发布检查项。

## 关键要点

- 封装 = 多轨组织 + 时间戳同步 + 索引 + 元数据。
- moov 位置是点播首开的经典坑；faststart 是标配，fMP4 是方向。
- TS 的小包设计解释了它为什么适合直播切片。
- 容器决定「怎么装」，传输协议决定「怎么运」——下一阶段的主角。
